# 06. Передача в разработку и работа аналитика по этапам

## Этапы работы аналитика

### 1. Анализ и сбор требований

- **Цель:** понять боли стейкхолдеров, текущий процесс управления и точки потерь данных.
- **Вход:** запрос от Алекса: «срывы сроков, простои, неясно, где узкое место».
- **Что уточнить у заказчика:**
  - как сейчас принимают решение о запуске материалов;
  - какие отчёты используют (OEE, загрузка);
  - где теряются данные (ручной ввод, задержки);
  - кто и как фиксирует простои;
  - как часто обновляются текущие отчёты.
- **Кому передаю:** стейкхолдеры Алекс, Боб, Лу, Стейси.
- **Критерий готовности:** задокументированы боли всех стейкхолдеров; составлена AS-IS диаграмма; идентифицировано главное ограничение: метрика загрузки всех ресурсов.
- **Где ограничение в работе аналитика:** стейкхолдеры дают противоречивую информацию; Алекс не может выделить время на интервью.

### 2. Формализация (ТЗ, схемы, метрики)

- **Цель:** спроектировать витрину данных, дашборды и метрики, которые устраняют ограничение.
- **Вход:** AS-IS диаграмма, таблица болей, утверждённые бизнес- и пользовательские требования.
- **Что уточнить у заказчика:**
  - какая частота обновления данных нужна;
  - какие пороги для статусов (зелёный / жёлтый / красный);
  - какие поля должны быть в витрине;
  - кто какие дашборды видит (ролевая модель);
  - какую метрику считать главной (Throughput или OEE).
- **Кому передаю:** Алекс (утверждение метрик), Лу (финансовые T, I, OE), Боб (удобство дашбордов).
- **Критерий готовности:** ER-диаграмма согласована; спецификации 5 дашбордов утверждены; TO-BE диаграмма процесса готова; задачи для дизайнера написаны.
- **Где ограничение:** Алекс навязывает старые метрики (OEE, загрузка); Лу не понимает Throughput (cost world); Боб говорит «это слишком сложно».

### 3. Передача в разработку

- **Цель:** обеспечить чёткую передачу требований BI- и DE-разработчикам для реализации без переспросов.
- **Вход:** утверждённая ER-диаграмма, спецификации дашбордов, user stories, TO-BE схема.
- **Что уточнить:** какой SLA по обновлению данных; какой технологический стек; какой источник данных; кто будет тестировать; какие приоритеты для первого релиза.
- **Кому передаю:** BI-разработчик (дашборды), DE / ETL-разработчик (витрина), тестировщик (QA).
- **Критерий готовности:** user stories написаны в формате Gherkin; приёмочные критерии указаны для каждой метрики; DDL витрины передана; приоритеты MoSCoW согласованы.
- **Где ограничение:** разработчики не понимают бизнес-контекст; нет инфраструктуры для сбора данных в реальном времени; бюджет не позволяет сделать всё сразу.

## Чек-лист перед передачей задачи в разработку

- [ ] Указана частота обновления данных
- [ ] Описаны все метрики с формулами
- [ ] Заданы пороги срабатывания (зелёный / жёлтый / красный)
- [ ] Указаны критерии приёмки
