# 02. Требования

## Бизнес-требования

| ID | Требование | Приоритет |
|---|---|---|
| BR-01 | Завод должен увеличить пропускную способность (Throughput) как минимум на 15% в течение 3 месяцев | Высокий |
| BR-02 | Завод должен сократить незавершённое производство (WIP) на 50% без снижения отгрузок | Высокий |
| BR-03 | Завод должен выполнять заказы клиентов в обещанные сроки с точностью не менее 95% | Высокий |
| BR-04 | Завод должен перейти от реактивного управления к проактивному (предсказание неполадок за 2 часа до возникновения) | Высокий |
| BR-05 | Завод должен выявлять ограничение (bottleneck) и управлять им как основным рычагом роста | Высокий |

## Пользовательские требования

| ID | Требование | Приоритет |
|---|---|---|
| UR-01 | **Алекс:** каждое утро видеть текущий bottleneck и прогноз его загрузки на 8 часов вперёд | Высокий |
| UR-02 | **Алекс:** видеть глобальные метрики T (Throughput, пропускная способность), I (Inventory, запасы), OE (Operating Expense, операционные расходы) вместо локальной загрузки станков | Высокий |
| UR-03 | **Боб:** получать ранжированный список заданий на смену с учётом бутылочного горлышка | Высокий |
| UR-04 | **Боб:** видеть, какие действия предпринять, вместо очередного громкого проекта | Высокий |
| UR-05 | **Лу:** получать отчёт T, I, OE в единой витрине, а не из трёх разных мест | Высокий |
| UR-06 | **Рабочий:** видеть на дисплее станка «что делать следующим» и «когда будет материал» | Средний |
| UR-07 | **Стейси:** видеть тепловую карту WIP по станкам и очередь перед bottleneck | Средний |

## Функциональные требования

| ID | Требование | Критерий принятия |
|---|---|---|
| FR-01 | Система автоматически фиксирует время прихода и ухода каждой детали с каждого станка (например, по штрихкоду) | **Дано:** деталь поступила на станок. **Когда:** сканер зафиксировал. **Тогда:** запись появилась в витрине |
| FR-02 | Система вычисляет время ожидания перед каждым станком как разницу между `arrival_time` на текущем станке и `departure_time` с предыдущего | **Дано:** две последовательные операции. **Тогда:** `waiting_time` рассчитан автоматически |
| FR-03 | Система ранжирует все станки по среднему времени ожидания за последние 60 минут и выделяет TOP-1 как «текущий bottleneck» | **Дано:** очередь перед станком А выросла до 6 часов. **Тогда:** дашборд показывает станок А красным |
| FR-04 | Система отображает на дашборде ритм bottleneck (ед/час), очередь перед ним (в часах) и рекомендует максимальное количество для запуска | **Дано:** ритм 20 ед/час, очередь 8 часов. **Тогда:** рекомендация «запустить не более 160 ед» |
| FR-05 | Система рассчитывает Throughput (T) = выручка от проданного − прямые материальные затраты на уровне заказа, продукта и завода | Заказ продан, T рассчитан и добавлен в отчёт |
| FR-06 | Система рассчитывает Inventory (I) как стоимость WIP + готовой продукции + сырья | Даны данные со склада и цеха, I рассчитывается ежедневно |
| FR-07 | Система рассчитывает Operating Expense (OE) без учёта прямых материалов | Даны операционные затраты, OE рассчитан |
| FR-08 | Система хранит историю bottleneck за 30 дней для анализа миграции ограничений | *Критерий уточнить* |
| FR-09 | Система отображает тепловую карту WIP по станкам (красный — ближайший к ограничению) | Есть данные по всем станкам, показывается тепловая карта с цветовой градацией |
| FR-10 | Система ранжирует заказы в очереди перед bottleneck: заказ с меньшим временем прохождения bottleneck получает более высокий приоритет | **Дано:** 2 заказа в очереди. **Когда:** рассчитано время прохождения bottleneck. **Тогда:** заказ с меньшим временем стоит выше |

## Нефункциональные требования

| ID | Категория | Требование | Критерий принятия |
|---|---|---|---|
| NFR-01 | Производительность | Текущий bottleneck обновляется не реже 1 раза в минуту | Время от данных до отображения ≤ 60 сек |
| NFR-02 | Доступность | Система доступна в производственные часы (2 смены, 16 часов) | Uptime 99,5% (простои не чаще 1 часа в неделю) |
| NFR-03 | Точность данных | Расхождение между автоматической фиксацией и ручным учётом | Не более 1% по количеству операций |
| NFR-04 | Масштабируемость | Витрина поддерживает до 50 станков и 10 000 событий в час | Пиковая нагрузка без потери данных |
| NFR-05 | Безопасность | Доступ к финансовым метрикам (T, I, OE) только у Алекса и Лу | Ролевая модель: 2 роли |
| NFR-06 | Обучаемость | Новый пользователь учится читать главный дашборд без инструктора | Время onboarding ≤ 15 минут |
| NFR-07 | Надёжность | При потере данных с RFID дашборд показывает серую зону, а не экстраполирует | Поведение при потере данных |
| NFR-08 | Прогнозирование | Система предсказывает возникновение bottleneck за 2 часа до события | Точность прогноза ≥ 80% |
